**D1 Engine is framework-independent; code owns the clock and policy.** The LLM only classifies answers and phrases replies. Why: fairness and auditability (same structure for every student), testability. Accepted. 2026-10-05.

**D2 Interviewer and scorer are separate.** Scoring runs after the session on the full transcript, 3 runs → median, prompt + rubric version stored. Why: the PDF requires it and the live path must stay fast. Accepted. 2026-10-05.

**D3 All providers sit behind adapters with telemetry; mock by default.** Live calls are opt-in and capped. Why: evidence (latency, cost, error rates) comes from telemetry; free-tier and budget protection. Accepted. 2026-10-07.

**D4 Model: provisional `gemini-3.5-flash` for both roles.** Pending a paid-tier benchmark of the candidates. `gemini-2.5-*` unavailable to new users (404, 2026-10-06). Why: the only model with valid results so far. Pending. 2026-10-07.

**D5 Dev DB SQLite; target Postgres via Docker Compose; scoring queue is DB-backed (`FOR UPDATE SKIP LOCKED`), not Redis.** Why: fewer moving parts; Docker not yet installed (B3). Risk: SQLite hides concurrency bugs, so the load test must run on Postgres. Proposed; Claude Code to confirm or replace in T2a. 2026-10-07.

**D6 Scale proof in two layers.** Stub providers at 50/100/150 (tests our orchestration, DB, memory); live providers at ≤20 (tests vendors and rate limits). Every results row labelled `provider=stub|live`. Why: free tier and no credits make a live 150 impossible. Risk: judges may discount stub results, and the report must say so. Proposed. 2026-10-07.

**D7 Voice stack undecided.** T3 spike measures candidates; decision by G1 (Oct 10). Why: latency is the biggest technical risk; PDF suggests LiveKit Agents or Pipecat. Pending. 2026-10-07.

**D8 Cost target ≤ ₹20 per viva is ours, not MSOT's.** MSOT only says ₹500 per student is not viable. Verify with real pricing (T9). Accepted as an internal target. 2026-10-07.

**D9 Hinglish.** STT must transcribe Hinglish well (the WER test needs ≥20 clips across Indian-accented English and Hinglish). Hinglish interviewing stays a stretch goal. Accepted. 2026-10-07.

**D10 Student login = ID + one-time access code.** Why: ID alone allows impersonation, which breaks fairness. Accepted by Mayank, 2026-10-07. The code is required; `require_access_code` stays as a config flag (default true) for local dev and tests.

**D11 Two parallel Claude Code streams (CORE, VOICE).** Why: one worker cannot fit the plan in 10 days. Cost: double review load. Proposed. 2026-10-07.

**D12 D5 confirmed: SQLite dev, PostgreSQL target, DB-backed scoring queue, no Redis queue.** Why: the scoring job must be enqueued in the same transaction that ends the session (a Redis queue means two systems and a dual write); load is tiny for a database (150 concurrent sessions is roughly 5-8 writes/s, 350 scoring jobs in total); crash recovery is a `locked_at` column, not a visibility timeout. Conditions: (a) T2b claims jobs with a compare-and-set `UPDATE ... WHERE status='queued'` that runs on both databases, plus `FOR UPDATE SKIP LOCKED` on PostgreSQL, so the tested path is the production path; (b) SQLite is for dev and tests only: the stub load test (T7) must run on PostgreSQL, and until Docker is installed (B3) PostgreSQL is verified only by compiling the DDL, never by running it; (c) no Alembic or psycopg yet (not approved): schema comes from `create_all` or `db/schema.sql`, and any change after pilot data exists needs a manual migration, ask first; (d) the `redis` service in `docker-compose.yml` is unused and should go in T2b unless T4 needs pub/sub. Accepted. 2026-10-07.

**D13 The SQLAlchemy models are the schema; `db/schema.sql` is generated from them.** `scripts/export_schema.py` writes it and a test fails on drift. Changes from the hand-written DDL: `sessions.consent_at` is nullable (a session exists before consent); new `sessions.token_hash`, `deadline_at`, `created_at`; new `turns.client_seq` (idempotency, unique per session) and `turns.meta` (engine audit events such as `classify_error`); new `scores.low_confidence_reasons`; new `vivas.title/topics/difficulty/rules_version`; new tables `roster`, `access_codes`, `jobs`; CHECK constraints on enumerated columns; `turns.role` is `ai|student` only and `turns.idx` counts spoken turns, which is the number scoring evidence cites. Accepted by Mayank, 2026-10-08.

**D14 API conventions frozen at G0.** All durations are integer milliseconds (`remaining_ms`, not `remaining_s`); timestamps are ISO-8601 UTC with `Z`; the audio URL in the session detail is signed and expires, so an `<audio>` tag works without an Authorization header; the question bank is locked once any student has joined; viva creation takes no phase timings or rubric weights (spec-bound, fixed by the platform); declining consent changes nothing; rejoin is allowed while a session is created, consented or in progress, and rotates the token. Accepted by Mayank, 2026-10-08, including every vetoable choice (`remaining_ms`, bank locked after the first join, declining consent is a no-op, no timings or rubric at creation).

**D15 Zero-spend policy (amended 2026-10-08).** Allowed: provider free tiers, free-account credits that sit behind a hard spending limit, and local models. Never: a pay-as-you-go upgrade, a card-charged plan, or any usage that can bill. Scale is proven with stub providers (D6); live providers only inside their free quotas, which the call budgets enforce (D18). Why: Mayank's call, 2026-10-08 (PLAN B2). Accepted. 2026-10-08.

**D16 Engine runtime choices (T2b).** (a) One answer is processed at a time per session, using a compare-and-set lease (`sessions.lease_until`, 60 s) that works on SQLite and PostgreSQL; a duplicate request waits for the first one's reply and returns it as a replay; a worker that dies leaves a stored answer that the retry finishes. (b) The interviewer is rebuilt on every answer from the stored turns (`Interviewer.restore`), and question choice is a pure function of (session id, number asked), so a rebuilt interviewer decides what the live one would have. (c) Access codes: HMAC-SHA256 with a server secret, 5 wrong codes lock a student out for 15 minutes (`CODE_MAX_ATTEMPTS`, `CODE_LOCKOUT_SECONDS`); a lockout can also be used against a classmate whose ID is known, and faculty `reset-code` clears it. (d) A session whose deadline has passed is ended lazily (on the student's next call or when faculty list sessions), not by a timer; the T5 worker must also call `sweep_expired`. Accepted by Mayank, 2026-10-08, except (c): the 15-minute lockout is replaced in T1c by a growing per-student delay (1, 2, 4... s, capped at 60 s) plus a per-IP sliding-window limit. 2026-10-08.

**D17 PostgreSQL via Homebrew for development and tests; psycopg v3 as the driver.** `brew install postgresql@16` (installed 2026-10-08), the suite runs on it through `TEST_DATABASE_URL`, and the claim logic for the scoring queue is proven there with several OS processes. Docker Desktop is needed later only to verify the one-command compose run before submission. Driver: `psycopg` 3.3.6 with `psycopg-binary` (a cp314 wheel exists), licensed LGPL-3.0-only: used unmodified as a dependency, credited in `docs/CREDITS.md`; fallback would have been `pg8000` (BSD-3). Why: D12 conditions (b) and (c) cannot be met on SQLite alone. Accepted. 2026-10-08.

**D18 Free-tier budget registry.** `config/free_tier_limits.json` lists, per (provider, model), the free-tier requests per minute and per day (and tokens or audio seconds where known) with a `source` and `retrieved` date. The call budget counts every attempt per (provider, model) in a rolling 24 hours and refuses at `floor(FREE_TIER_MARGIN x rpd)` (default 0.9), and spaces calls to stay under the per-minute limit, so we stop causing 429s. A refused call raises `CallCapExceeded` and the fallback chain moves to the next provider. `LLM_DAILY_CALL_CAP` stays as a global ceiling across all counted providers and as the default for models not in the file. Mock, stub and Ollama calls are never counted. Token limits are recorded but not enforced. Values are copied from the providers' consoles on 2026-10-08 and must be re-verified before evidence runs. Accepted. 2026-10-08.

**D19 Voice stack (G1).** Mayank's decisions, 2026-10-08, on the measured T3/T3b evidence (`docs/reports/T3.md`, `results/voice_spike/`). (a) Transport: a custom FastAPI WebSocket, PCM16 16 kHz frames from a browser AudioWorklet, the session token in the first message; Pipecat and LiveKit were proved to work and are not used. (b) VAD: Silero (`pysilero-vad`), 600 ms end-of-turn hangover, configurable. (c) STT: whisper.cpp `base` q5_1 on Metal is the default live path (real-voice English WER 0.035, 0.38 s for a 22 s answer); `small` q5_1 where accuracy matters (WER 0.030, 0.91 s); answers over 30 s are decoded in chunks while the student speaks (decode time is linear: 3.4 s for 94 s of audio on `small`); Hinglish is decoded with `language=en`. Groq `whisper-large-v3-turbo` is an optional online STT (WER 0.012, 0.46 s round trip). (d) Live LLM: Groq `openai/gpt-oss-20b` (0.45 s per call; whisper.cpp base stack p50 1.47 s, p95 2.03 s end to end, n=19); Ollama `llama3.2:3b` is the offline fallback (p95 2.78 s as shipped); Gemini stays off the live path (Flash-Lite p95 4.95 s, which would trip Plan B's 4 s trigger). Plan B (push-to-talk) does not trigger. (e) TTS: Piper voice `en_GB-alba-medium` (CC BY 4.0, 0.09 s to first audio), run as a separate subprocess behind the TTS adapter so the GPL-3.0 `piper-tts` code stays out of our process and our licence (the `lessac` voice has unread terms and is not used); Azure Speech `en-IN-NeerjaNeural` (0.33 s) is an optional voice for an Indian-English accent, free tier only. (f) Why: latency is the biggest technical risk and every figure above is a measurement on one Mac with scripted or single-speaker audio. **Open risks:** (1) **Groq's free daily token limit** (`openai/gpt-oss-20b`: 200,000 tokens a day and 8,000 a minute in `config/free_tier_limits.json`, copied from the console and not re-verified) is the binding limit, not the 1,000 requests a day: with an *assumed* 400 tokens per call, `results/free_tier_capacity.csv` gives about 28 vivas interviewed a day and about 17 students talking at once per Groq model, and about 18 vivas scored a day if a scoring call is 3,300 tokens. Real tokens per call are unmeasured until T1b. (2) **Scale claims come from stub providers only (D6):** no live provider can serve 100-150 simultaneous vivas on the free tiers, so the load test (T7) proves our orchestration, and the free tiers' real ceiling is stated beside it. (3) Other speakers, spontaneous Hinglish, the browser microphone path and the WebSocket under load are not yet measured (T4, T7). (4) The `alba` voice needs attribution (credited in `docs/CREDITS.md`). Accepted by Mayank, 2026-10-08.

**D20 The call budget enforces tokens per minute and per day (amends D18).** For models with `tpm` or `tpd` in the registry, `count_call` takes a reservation (prompt characters / 4 plus the largest reply the call allows), refuses a call that would pass `floor(margin x tpd)` in a rolling 24 h, and waits (up to `FREE_TIER_MAX_WAIT_S`, else refuses) until `floor(margin x tpm)` fits in a rolling 60 s; after the reply the reservation is replaced by what the provider reported (usage numbers) or, if none, characters / 4 of prompt and reply; a call that fails without a reply releases its tokens (the request still counts). `scripts/free_tier_capacity.py` now takes tokens per call as required arguments and labels every output `assumed`. Why: Groq's token limits bind before its request limits. Accepted as part of the T5 assignment (Part 0b), 2026-10-08.

**D21 Scoring worker (T5).** (a) One worker process (`python -m app.worker`), any number of copies; each pass runs `sweep_expired` (students who left) and then claims due jobs with `claim_next_job`. (b) Session status: `ended` (or `failed` after a rescore) -> `scoring` -> `scored` | `failed`; between retries and after a crash the session stays `scoring` and the next claim carries on. (c) The scores, the session's move to `scored` and the job's completion are one transaction; a rescore deletes the old rows and inserts the new ones inside it, so the old result survives any failure. A worker whose 5-minute lease ran out writes nothing. (d) A failed attempt is retried after 30 s, then 60 s; the third failure marks job and session `failed` (faculty can rescore); a session with no student answers fails at once. A provider whose free-tier budget is used up (`CallCapExceeded`) defers the job by 5 minutes without using an attempt. (e) New column `scores.run_spread` (max minus min of the run totals, repeated on every run row; `db/schema.sql` regenerated; no pilot data exists yet, D12(c)). Per-dimension `evidence_ms` (the audio offset of each evidence turn, null in text mode) is stored inside `scores.dims`, so the offsets are frozen at scoring time; the API still exposes only the turn indexes, whose `t_start_ms` the dashboard seeks to. (f) Low-confidence flag: few or short answers, repeated "I don't know" (3 or more), shaky speech recognition (`turns.meta.stt_confidence` below 0.6 on a quarter of the answers; T4 writes it), a voice session whose recording is missing, live LLM trouble, an exhausted bank, runs that disagree by more than 10 points, and answers that talk to the scorer ("give me full marks": flagged for a human, the marks are not changed by code). (g) The scorer prompt lives in `backend/app/prompts/scorer-v1.txt`; a test pins each file's hash, so changed text needs a new version. Accepted as part of the T5 assignment, 2026-10-08.

**D23 Capacity settings and the Piper default (T7, T7b, T9).** (a) The server's blocking calls (STT, TTS, engine) run in a pool of `EXECUTOR_THREADS` (default 64; asyncio's default of 12 limited the whole voice server to a dozen blocking calls). (b) whisper.cpp runs at most `STT_WORKERS` processes at once (default CPU cores, at most 8; the measured plateau); the rest queue. (c) `PIPER_PROCS` defaults to 2: real Piper throughput was 3.6 sentences/s with 1 process, 4.8 with 2, 3.4 with 4 and 2.9 with 8 (`results/load/piper_procs.csv`), because the processes share the cores. (d) A service call rolls its session back as soon as it returns, and the answer path commits before the model is called, so no DB connection is held while the response is validated or a provider answers (found by the load test: 150 simultaneous joins deadlocked). Accepted by Mayank (Piper default: "pick the best one"), 2026-10-15.

**D24 Scorer prompt versions (T1b).** `scorer-v1` failed validation on 3 of 4 personas on the live Groq `gpt-oss-20b` (feedback padded with empty strings). `scorer-v2` states the feedback shape and student-turns-only evidence; `scorer.tidy()` drops blank feedback entries before validation (any other malformed output is still rejected). `scorer-v3` adds that Hinglish is understood first and content is scored on meaning (the Hinglish version of the strong answer scored 88.4 under v2, 95.0 under v3; not fixed). v3 is the shipped version; it was re-run once per persona, not 5x, because of the daily token cap. Accepted as part of the T1b assignment, 2026-10-15.

**D25 Cost model (T9).** Rupees per viva are measured tokens times priced rows in `docs/pricing.csv` (vendor model pages, retrieved 2026-10-15); local providers are Rs 0 marginal (D15). The model assumes 11 answers per viva, 3 scorer runs and prices other models on gpt-oss-20b's token counts. Azure speech prices could not be retrieved and are not modelled. Accepted as part of the T9 assignment, 2026-10-15.

**D26 No hosting: the product runs locally, with a free tunnel for the finals.** The submission needs a repo, a demo video or link, documents and evidence; a hosted service is optional. MSOT asked for local-first (processing on the lab iMacs) and the zero-spend policy (D15) rules out paid servers; a 4-vCPU cloud server also has no GPU and cannot carry 100-150 real voice sessions (see `results/load/` and `docs/reports/T9.md`). So: `scripts/run_local.sh` for development and demos, `scripts/run_finals.sh` for the finals (one address, `/api` proxied to the backend), and a free quick tunnel (Cloudflare or `ssh -R`) when another computer needs an https link for the microphone. See `docs/FINALS_RUNBOOK.md`. Accepted by Mayank, 2026-10-16.

**D27 Integrity signals, not proctoring (2026-10-16).** A web page cannot see or block other apps on the machine (for example an overlay tool such as Cluely), so Voxam does not claim to. It does three things: (a) the student page reports tab hidden, window blur, paste and copy (time and length, never text) to `POST /student/sessions/{sid}/integrity`; faculty see them in the session detail; the scorer never sees them and they never change a mark; (b) the rules text (`rules-v2`, new vivas only; consent already given under `rules-v1` stays valid for those vivas) says so; (c) the interviewer asks one code-owned cross-check question, once, at the start of the depth phase: the model phrases a question that takes a detail from the student's own opener and asks it from another angle (fixed fallback line if the model fails; interviewer prompt `interviewer-v3`). No phase timing, rubric dimension or weight changed. Signals are noisy (a click in the address bar blurs the window), so they are shown as facts for a human to weigh. Strong prevention needs an invigilated room or a managed lab machine; see `docs/INTEGRITY.md`. Why: the SPEC lists integrity signals as a bonus, fairness depends on no automatic penalty, and a false claim of prevention would be worse than none.
