# T7 Load harness: ⚠️ partial   (2026-10-14, VOICE)
Harness built and run; it found and fixed one outage-class bug and two capacity limits. **Nothing here proves vendor capacity**: STT, TTS and the LLM are models of measured behaviour (`provider=stub`), the harness and the server share one machine, and no real whisper.cpp / Piper / Groq ran under load. Real concurrency beyond ~25 accelerated sessions is **not** shown.

- Changed: `app/loadmodel.py` (modelled STT / TTS / LLM, read from `results/`), `VOICE_PROVIDER=modelled` and `LLM_CHAIN=modelled`, `scripts/load_test.py` (async bots over the real API and WebSocket, fresh PostgreSQL per run, CPU / memory / DB connections sampled each second), `scripts/piper_concurrency.py` (real Piper by process count).
- Changed (fixes found by the load test): (1) **DB connection held until the response was validated** -> deadlock at 150 simultaneous joins, `app/api/deps.py`; (2) asyncio's 12-thread default pool carried every STT / TTS / engine call, `app/api/main.py` lifespan, `EXECUTOR_THREADS` (default 64); (3) real whisper.cpp had no process cap, `STT_WORKERS` (default cores, at most 8); (4) sessions starting together could each start their own Piper processes (lock in `providers.py`).
- Evidence (all `results/load/*.csv`, sidecar `provider=stub`, sha `be0cdb5`, clean tree, one uvicorn process, PostgreSQL):
  - Method: each bot answers 3 times, one answer every 15 s (about 5x faster than a real viva, which is roughly one answer per 80 s: **assumption**, so "real vivas" below = answers/s x 80). Pass = no dropped session, error rate <= 1 %, server p95 <= 4,000 ms.
  - `local_llm_unlimited.csv` (LLM not limiting): 10 and 25 sessions **pass** (p95 3.0 s and 3.1 s; 25 sessions = 2.0 answers/s, about 160 real vivas). 50 sessions: p95 5.5 s, no drops, 3.8 answers/s (about 300 real). 100: 8 dropped, p95 15.0 s. 150: 12 dropped, p95 30.4 s. **Throughput plateaus at 3.1-3.9 answers/s; beyond it, latency grows with the queue** (STT p95 4.0 s at 50, 10.0 s at 150).
  - `free_chain_107rpm.csv` (107 requests/min, whole free chain): same shape; 25 pass (p95 3.4 s), 50 p95 25.7 s, 150: 20 dropped, 3 pool timeouts, 40 degraded turns. **Runs are 3 answers per session, so they end before the minute window binds: the 25-session pass does not prove sustained capacity.**
  - `one_groq_model_27rpm.csv` (one Groq model): 10 pass; 25 sessions p95 61.0 s (8 degraded turns). One model cannot serve more than a handful.
  - `burst_unlimited_llm.csv` (everyone answers at once): 50 p95 9.5 s, 100 p95 27.3 s with no drops, 150: 9 dropped, p95 43.1 s.
  - `storm_429_50.csv` (80 % of LLM calls rejected for 25 s at 50 sessions): 0 dropped, 6 degraded turns, p95 5.5 s (same as without the storm).
  - Findings kept as before/after: `before_pool_fix_local_llm_unlimited.csv` (150 sessions: all joins failed), `before_executor_pool/` (12-thread pool), `executor_64_piper_1proc/` (one Piper process).
  - Real Piper (`results/load/piper_procs.csv`, `provider=live`, TTS alone; sidecar sha is `8843dd4+dirty` because the script was run before it was committed, the committed script is the same file): 1 process 3.6 sentences/s, **2 processes 4.8**, 4 processes 3.4, 8 processes 2.9. **More Piper processes do not add throughput; they share the cores.**
  - `python -m pytest -q --ignore=backend/tests/test_voice_spike.py` -> **`503 passed, 2 skipped`** (`test_voice_spike.py` does not collect in this venv: `jiwer` missing, the known main-is-red item from T5). `python scripts/check_secrets.py` -> clean.

  4. At 150 on the free chain a **DB connection is held across the LLM wait**: 61 connections in use, 3 pool timeouts. Not fixed.

- Risks found:
  - **The free chain cannot serve 150 simultaneous students in the sustained case** (the budget, not the code). Calls per answer are not in the CSV; measure them before quoting a student count.
  - `PIPER_PROCS` default is 1; the measurement says 2 is best (+35 %). Left at 1: your call.
  - The harness's modelled LLM per-process rpm window multiplies with `--workers`; real budget registry is per process too (state is in memory).
  - The 4 s p95 pass mark is mine (spec has no number for server-side answer latency); the 25-session point is at 3.1 s, the margin is thin.
