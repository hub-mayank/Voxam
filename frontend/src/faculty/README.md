## Open questions

- Viva creation: `POST /faculty/vivas` exists in `docs/API.md` and `docs/openapi.json`, but `frontend/src/api/faculty.ts` has no create-viva method. Should creation eventually live on the viva list, and which card owns it? The table assigns it there provisionally for endpoint coverage, not as PA-1 work. Mayank/the foundation owner must resolve the missing typed method before implementation; do not call fetch directly or invent a hook.
- Navigation: `frontend/src/faculty/routes.tsx` has no routes for bank upload, roster upload or export/release. Should these be separate pages or sections of an existing page, and how will they receive `vivaId`? No paths are invented here. Stop and ask Parth before any router change.
- Counts: `session_counts` contains only statuses present in the database and may be empty. Should the list show every defined status with zero for absent keys, or only statuses returned by the API? These are session statuses, not a single viva status.
- Seeded proof: `scripts/run_local.sh` creates LOCAL questions and roster entries without sample sessions; `scripts/seed_demo.py` creates populated DEMO dashboard states. Which dataset should be used for each review screenshot? The team plan names the LOCAL script, while the API guide describes the DEMO seed.
- Source notation: this table uses the exact OpenAPI placeholder `{viva_id}`; the API guide abbreviates it as `{id}` and the browser route uses `:vivaId`. They identify the same viva. All 17 faculty method/path combinations in OpenAPI are mapped above, including the audio endpoint described through `audio.url` in the guide.
